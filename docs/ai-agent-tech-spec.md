# Техническая спецификация: система мониторинга воздушных тревог

Спецификация предназначена для AI-агента, который должен реализовать систему с
функциональностью, эквивалентной описанной ниже. Документ описывает только
техническую сторону: архитектуру, данные, алгоритмы, API, инфраструктуру.
Вопросы визуального оформления и пользовательского интерфейса вне области
действия спецификации.

---

## 1. Назначение системы

Система обеспечивает:

1. Периодический опрос внешнего API `alerts.in.ua` для получения актуального
   состояния воздушных тревог по регионам Украины.
2. Хранение текущего и исторического состояния тревог в PostgreSQL + PostGIS.
3. Геопространственное разрешение подписок пользователей (точка lat/lon →
   иерархия региона: область → район → община/город).
4. Доставку push-уведомлений (Firebase Cloud Messaging) подписчикам при
   изменении состояния тревоги в их регионе.
5. Отдачу данных для картографического клиента: геометрия регионов, слой
   активных тревог, угрозовые оверлеи, оккупированные территории, граница
   Украины.
6. Ингест сообщений из Telegram-каналов и их разбор с помощью LLM для
   построения угрозовых оверлеев (БПЛА, ракеты, артиллерия).
7. Импорт и обновление справочника регионов и их геометрий.

## 2. Компоненты системы

| Компонент | Тип | Назначение |
|-----------|-----|-----------|
| API-сервер | Долгоживущий HTTP-процесс (NestJS) | Публичный REST API, кэширование, инвалидация |
| Poll-воркер | Короткоживущий процесс, запускается таймером (~15 сек) | Опрос alerts.in.ua, детект изменений, запись в БД, постановка пушей в очередь |
| Push-воркер | Короткоживущий процесс, таймер (~15 сек) | Отправка накопленных push-уведомлений через FCM |
| Telegram ingest-воркер | Короткоживущий процесс, таймер | Забор сырых сообщений из Telegram-каналов |
| Telegram parse-воркер | Короткоживущий процесс, таймер | Разбор сырых сообщений LLM, создание угрозовых оверлеев |
| Import-воркер | Короткоживущий процесс, таймер | Импорт справочника регионов из XLSX |
| Archive-воркер | Короткоживущий процесс, ежедневный таймер | Архивация протухших угрозовых оверлеев |
| Rebuild alert layer | Ручной/по требованию | Пересборка таблицы `alert_layer_features` |
| Geometry import | Ручной | Импорт GeoJSON геометрий регионов |
| Мобильный клиент | Android-приложение | Получение данных API, polling, FCM, офлайн-геометрия |

Воркеры — это отдельные точки входа, каждая компилируется в свой JS-файл и
запускается независимым `node`-процессом. Они **не** являются частью API-сервера
и не имеют общей памяти с ним — всё взаимодействие только через БД и Redis.

## 3. Технологический стек

| Слой | Технология | Требования |
|------|-----------|-----------|
| API | NestJS 10 + TypeScript | REST, Swagger-документация, ValidationPipe (whitelist, transform, forbidNonWhitelisted) |
| БД | PostgreSQL 15 + PostGIS 3 | Raw SQL через `pg` Pool (без ORM), транзакции через PoolClient |
| Кэш/очереди | Redis (ioredis) | Общий кэш между процессами, паттерн-инвалидация |
| Push | Firebase Admin SDK | Метод `sendEach` батчами |
| Telegram | Библиотека `telegram` (MTProto) | Пользовательская сессия (session string) |
| LLM | Минимум один провайдер (Gemini/DeepSeek/Grok) | JSON-вывод структурированного разбора, опциональный "thinking"-режим (по умолчанию выключен) |
| Мобильный клиент | Kotlin, minSdk 26 | FCM, HTTP-клиент с polling, локальные GeoJSON-ассеты |

Пул БД: `max: 20`, `idleTimeoutMillis: 30000`, `connectionTimeoutMillis: 2000`.
Все бизнесовые метки времени — `NOW() AT TIME ZONE 'Europe/Kyiv'`.

## 5. Семантика статусов тревог (критически важно)

Источник возвращает IoT-строку статусов (позиционная строка по индексам
регионов) и `active.json` со списком активных алертов и атрибутами.

| Статус | Смысл | Правило обработки |
|--------|-------|-------------------|
| `A` | Полностью активен | Заливать/показывать как активный |
| `P` | Частично активен (активны не все дочерние) | **НЕ** считать сам регион активным; активными считаются только дети |
| `N` или пробел | Нет тревоги | Прозрачный |

**Уровень тревоги (alert_level: `red` | `yellow`)** существует только в
`active.json`; IoT-строка его не несёт. Поэтому каждый цикл опроса
обязательно запрашивает `active.json`, а детект изменений строится на
комбинированном хэше `IoT-строка + атрибуты active.json`. Изменение только
уровня (без смены статуса) **должно** инкрементировать `state_version`, но
**не** порождает событий и пушей.

Разрешение уровня по иерархии:

1. Собственная запись в `active.json` для данного uid.
2. Если нет — наследование от ближайшего предка, имеющего запись.
3. Родительские регионы (область/район) выводятся из активных потомков:
   **red побеждает** — родитель yellow только если все активные потомки yellow.
4. Жёлтые угрозы источник отдаёт в основном на уровне района/города, но
   IoT-строка помечает активными все общины внутри них — агрегированный уровень
   должен быть согласован (см. п. 3).

Особые типы тревог (артиллерия, уличные бои) хранятся в `alert_type` и
обрабатываются отдельно от бинарного статуса.

## 6. Цикл опроса (poll-воркер)

Каждый цикл (~15 сек, ≤2 запроса за цикл — не более 8 запросов/мин к внешнему
API):

1. Параллельно запросить IoT-строку статусов и `active.json` (Bearer-токен).
2. Вычислить комбинированный хэш. Если совпал с прошлым циклом — записать
   `alert_poll_cycles` (`changed = false`) и завершить без записи состояний,
   событий, пушей и кэш-работы. **Циклы без изменений не трогают кэш.**
3. При изменении — в одной транзакции:
   - UPSERT в `air_raid_state_current` по каждому изменившемуся uid (status,
     alert_type, alert_level, active_from, state_version);
   - вставка событий в `air_raid_events` (`started` / `ended` /
     `state_changed`);
   - синхронизация `subscription_runtime_state`;
   - постановка записей в `notification_dispatches` для подписок, чьё
     runtime-состояние изменилось (дедупликация: пуш только при реальном
     переходе статуса, не при каждом цикле).
4. COMMIT.
5. **Только после COMMIT** — обновление кэшей (см. раздел 8).
6. Записать `alert_poll_cycles` с фактическими хэшами/статусом HTTP.

## 7. Геопространственная логика

- Иерархия: **область → район → община/город**. Листья подписки —
  общины и города (`is_subscription_leaf = TRUE`).
- Разрешение точки: `ST_Contains(geom, ST_SetSRID(ST_MakePoint(lon, lat), 4326))`
  по листьям; результат включает цепочку `oblast → raion → hromada` + uid
  каждого уровня.
- Наследование статуса: если родитель активен, а ребёнок явно не перечислен —
  ребёнок наследует состояние родителя. Особый кейс: город с областным
  значением (м. Київ) наследует статус от соответствующей области.
- Кэш активных uid для рендеринга содержит **только листья** (`is_subscription_leaf
  = TRUE`). Районы и области в него не включаются — они закрашиваются
  активными детьми, а не собой.
- **PostGIS: для объединения смежных полигонов (граница Украины, маска)
  использовать `ST_Union` (или `ST_Buffer(ST_Collect(...), 0)`). Чистый
  `ST_Collect` даёт MultiPolygon без слияния и дыры на границах областей.**
- Геометрии отдаются клиенту на трёх уровнях детализации (LOD) для разных
  zoom-уровней карты.

## 8. Кэширование (двухуровневое)

**Уровень 1 — Redis** (общий, TTL): бандлы фич, бандл тревог, активные uid,
угрозовые оверлеи, результаты `resolve-point`. Используется для межпроцессного
обмена и инвалидации.

**Уровень 2 — in-memory JSON-кэш в API-процессе** (готовые сериализованные
строки): **разрешён ТОЛЬКО для статических данных** (граница Украины).

**КРИТИЧЕСКОЕ ПРАВИЛО**: нельзя использовать in-memory-кэш для данных о
тревогах. Poll-воркер не может инвалидировать память API-процесса без его
перезапуска. Инвалидация происходит только при реальном изменении состояния
(не на циклах 304/no-change), только post-commit:

- `map:bundle` — **пересборка свежими данными** (мобильный клиент опрашивает
  `/map/bundle`; без пересборки он получал бы протухшие данные до конца TTL);
- `alerts:current`, `alerts:active:uids` — пересборка свежими данными;
- `alerts:layer:response`, `features:*` (все геометрические бандлы) —
  инвалидация, ленивая пересборка по требованию;
- `resolve-point:*` — инвалидация по паттерну (ответы встраивают статусы;
  TTL 300 сек);
- публикация события `map:alerts:updated` (pub/sub) для уведомления
  заинтересованных процессов.

Telegram parse-воркер после COMMIT инвалидирует `threats:*` по паттерну +
`map:threat-bundle`; если разбор применил синтетические тревоги к
`air_raid_state_current` — вызывает тот же пост-коммит refresh.

TTL геометрических бандлов `features:*` — 1 час, но lookup статусов
пере-инжектится при чтении из `alerts:active:uids`.

## 10. Push-уведомления

1. Регистрация: клиент регистрирует `installation_id` + FCM-токен; токены
   обновляются через PATCH; неактивные (невалидные по ответу FCM) маркируются
   `active = false`.
2. Постановка в очередь — в транзакции обнаружения изменения состояния
   (раздел 6), на основании `subscription_runtime_state` (только реальные
   переходы статуса).
3. Отправка push-воркером: выборка queued-записей, отправка через FCM
   `sendEach` **батчами до 500 за запуск**, перевод в `sent`/`failed`.
   Ошибки невалидного токена деактивируют токен.
4. Payload содержит: регион (uid, title), тип события (начало/конец тревоги),
   `alert_type`, `alert_level`, `state_version` — достаточно для отображения
   и дедупликации на клиенте.

## 11. Telegram-ингест и LLM-разбор

- MTProto-клиент с пользовательской сессией (session string). Воркер
  обязан иметь RPC-таймаут (по умолчанию 60 сек): при зависании — уничтожать
  клиент, чтобы следующий запуск переподключился чисто.
- Ingest-воркер пишет сырые сообщения в `telegram_messages_raw` (`processed =
  false`), дедупликация по id сообщения.
- Parse-воркер выбирает неразобранные сообщения и отправляет LLM с
  промптом, требующим строгий JSON: тип угрозы (uav/kab/missile/artillery),
  точка/направление происхождения, цель/коридор, время актуальности.
  "Thinking"-режим LLM выключен по умолчанию (экономия ~95% completion-токенов),
  включается env-флагом.
- Результат: транзакционное создание `threat_visual_overlays` +
  `threat_vectors` (origin/target/corridor/danger_area), пометка сообщения
  `processed`. При необходимости — применение синтетических тревог к
  `air_raid_state_current` (с полным пост-коммит refresh кэшей).
- Ежедневный archive-воркер переводит протухшие оверлеи в архивный статус.

## 12. Импорт данных

- **Справочник регионов (import-воркер)**: разбор XLSX-каталога регионов →
  UPSERT `region_catalog` (uid, иерархия, `is_subscription_leaf`).
- **Геометрия (ручной запуск)**: импорт OCHA COD-AB GeoJSON → `region_geometry`
  + построение трёх LOD в `region_geometry_lod` (упрощение PostGIS-функциями).
- **Оккупированные территории (воркер по таймеру)**: загрузка актуального
  GeoJSON оккупированных территорий из внешнего источника, замена слоя.
- После любого обновления геометрии — инвалидация соответствующих `features:*`.

## 13. Мобильный клиент (функциональные требования)

Без требований к оформлению; перечислено только поведение:

- Регистрация установки: генерация/хранение `installation_id`, отправка на
  POST `/installations`, хранение FCM-токена и его обновление через PATCH.
- FCM-сервис: приём push, показ уведомления с данными payload (регион, тип
  события, уровень), обновление локального состояния без полного re-fetch.
- Polling: `/map/bundle` каждые ~30 сек; если `state_version` не изменился —
  скип обработки. `/map/threat-overlays` каждые ~60 сек.
- Дельта-синхронизация через `/alerts/statuses/delta?since_version=N`.
- Офлайн-фолбэк: геометрия регионов и индекс `uid → {title, region_type,
  bbox-центр}` поставляются как несжатые ассеты в APK (читаются через mmap);
  при недоступности сети клиент работает на последнем снапшоте.
- Подписки: создание пина по координатам через `resolve-point`, CRUD подписок,
  локальное хранение списка.
- Пуш-настройки на устройстве (вкл/выкл, фильтры) — локальные.

## 15. Развёртывание и эксплуатация

- Всё изолировано в одном каталоге на сервере (например `/srv/<app>/`) с
  релизами через symlink `current → releases/<latest>`.
- Каждый воркер — пара systemd-юнитов: `oneshot`-сервис + timer.
  **На таймерах обязателен `AccuracySec=1s`** (дефолтная точность systemd
  в 1 минуту убивает суб-минутные интервалы) и `TimeoutStartSec` (120–300с),
  чтобы зависший oneshot был убит и таймер мог сработать снова.
- API — `simple`-сервис на `127.0.0.1:<порт>`, наружу — reverse proxy
  (nginx) по IP.
- Ежедневный плановый рестарт API и ingest-воркера (таймер, ночь) для сброса
  накопившихся ресурсов.
- После каждого деплоя API перезапускается (сброс in-memory-кэша).
- На одном хосте могут сосуществовать чужие сервисы: не трогать их unit-файлы,
  каталоги и занятые порты; деплой-скрипт проверяет их работоспособность до
  и после деплоя и откатывается при провале health-check.

## 16. Нефункциональные требования

- Rate limit внешнего API: ≤ 8 запросов/мин (соблюдается 2 запроса/цикл × 4
  цикла/мин при интервале 15 сек).
- Старт API и воркеров — холодный старт допустим, но health-check должен
  проходить после деплоя.
- Любая ошибка внешнего API фиксируется в `alert_poll_cycles` с `error` —
  система не должна падать из-за недоступности источника.
- Все записи в БД, затрагивающие несколько сущностей, — в транзакциях.

## 17. Критические правила (нестандартные случаи)

1. **`status = 'P'`** — частично активный родитель. Не считать его активным;
   активны только конкретные дети. Иначе вся карта "заливается" ошибочно.
2. **In-memory-кэш запрещён для тревог** — только статика (граница Украины).
3. **Кэш-пишется/инвалидируется только post-commit.**
4. **Циклы без изменений не делают кэш-работу** — протухшие ключи лениво
   пересобираются из БД по требованию.
5. **`ST_Union`, а не `ST_Collect`** для сливаемых полигонов.
6. **`/map/alerts-layer` обязан включать `status` в properties** каждой фичи.
7. **Кэш активных uid — только листья подписок.**
8. **Изменение только `alert_level`** бампит `state_version` без событий и
   пушей.
9. **systemd-таймеры: `AccuracySec=1s` + таймаут убийства** — иначе один
   зависший запуск блокирует воркер навсегда.
10. **Telegram-клиент: RPC-таймаут + destroy при зависании.**

## 18. Критерии приёмки для AI-агента

- [ ] Проходит type-check (`tsc --noEmit`), продакшн-сборка без ошибок.
- [ ] API поднимается, Swagger доступен, health-check отвечает.
- [ ] Poll-воркер: на реальном/заглушечном источнике детектит started/ended/
      state_changed, пишет события и аудит циклов.
- [ ] Смена только уровня бампит `state_version` без событий/пушей.
- [ ] Родитель со статусом `P` не включается в активные uid для рендеринга.
- [ ] Жёлтый родитель при красном ребёнке — red.
- [ ] `resolve-point` возвращает полную цепочку иерархии; повторный запрос
      идёт из кэша.
- [ ] После изменения состояния: `/map/bundle`, `alerts:current`,
      `alerts:active:uids` отдают свежие данные сразу post-commit.
- [ ] Уведомление доходит до зарегистрированного токена при смене статуса
      региона подписки; повторный цикл без изменений не шлёт повторный пуш.
- [ ] `features:*` бандлы содержат `status: 'A'` у активных фич.
- [ ] Telegram parse создаёт оверлей из fixture-сообщения и инвалидирует
      `threats:*`.
- [ ] Зависший воркер убивается таймаутом, следующий запуск таймера срабатывает.
- [ ] Граница Украины отдаётся без дыр между областями (ST_Union).
